## 🔴 P1 输出 CSV 存在大量重复行（已取证，根因待最后确认）

**事实**：`spec_id_pic_color_cnt_260908.csv` 共 17,246 行，但 `(spec_id, color_id)` 去重后仅 **11,518** 对；2,397 对重复、涉及 8,125 行。重复行内容**整行完全一致**（name/piccount/appearance_count 都相同）。

**取证**：抽查 spec 77620（雷克萨斯 GX 2026）的每个颜色出现 5 次，5 个副本的下标散布（如 [2526, 2572, 2667, 2676, 3212]），2386/2397 个重复对**交错非连排**；spec 首次出现顺序非单调 —— 排除"单次顺序追加"，指向**多批次重叠抓取后合并/追加**。

**与断点续传设计冲突**：单进程顺序运行同一输出文件时，`load_completed()` 应使后续批次跳过已完成 `(spec_id, color_id)`。出现整对重复说明这些批次开始时续传未生效，可能机制（待确认）：
1. 多实例**并发**启动、同时向同一输出文件追加（各自启动时 completed 为空或过期）；
2. 多次用不同 `--output` 抓取后再手动合并文件；
3. 分批 `--limit` 测试重复覆盖同一批 spec 且未复用已完成文件。

**影响**：下游统计（appearance_count 分布、颜色覆盖率）被放大；`load_completed` 集合语义下不影响续传判定，但入库/分析前必须去重。

**修复建议**：
- 立即清洗：按 `(spec_id, color_id)` 去重重写（保留首次出现），并核对行数降为 11,518；
- 根上防复发：a) 若需并行加速 → 每个实例独立输出文件，最后统一去重合并；b) 落库改 SQLite 带 `PRIMARY KEY(spec_id, color_id)`，天然幂等；c) 至少给 `main()` 加"启动时统计输出文件重复率"的告警。

`image_list` 非空但**每个元素都缺 `picpath`**（页面结构变体/字段名变化）时：目录被创建（甚至为空/文件数不足）仍返回 `ok` 并写入 checkpoint —— 与"解析失败要重试"的语义矛盾，属于页面字段异常被静默吞掉。

**修复建议**：统计实际落盘数（含"已存在跳过"的旧文件），若 `image_list` 非空且有效落盘数 == 0 → 返回 `failed`（记入错误文件重试），不要 `checkpoint.add`。

## 🟡 P3 checkpoint 键不含 color_id，跨批次有误跳风险（crawler2）

`Checkpoint` 键与目录名均为 `(spec_id, 颜色名)`。若同一 spec 因改款/色号调整使 `color_id` 变化但**颜色名不变**（如都叫"珍珠白"），旧 checkpoint 会让新色号被跳过、目录被旧图占位（`count_files >= N` 判定"已满"）。流水线 1 的续传键是 `(spec_id, color_id)`，口径不一致。

**修复建议**：Excel 本就含 `color_id` 列 —— checkpoint 键与目录名升级为 `(spec_id, color_id[, 颜色名])`，`--retry` 错误文件同步带上 `color_id`；无 `color_id` 的旧错误条目按 `(spec_id, 名称)` 降级兼容。

## 🟢 P4 __NEXT_DATA__ 解析三处各写各的（跨文件一致性）

- crawler1 `fetch_next_data()`：BeautifulSoup 找 `script#__NEXT_DATA__`，仅替换 `&quot;`；
- crawler1 `_extract_count_from_next_data()`：regex 提取，替换 `&quot;`；
- crawler2 `parse_exterior_images()`：regex 提取，**无任何实体替换**。

页面实体化程度变化时三处行为将不一致（有的能解有的不能），且 `callist/claid=1` 结构路径重复硬编码。**建议收敛到 common.py 一个 `extract_next_data(html)` + `extract_exterior_callist(data)`**，两脚本共用，避免漂移。

## 🟢 P5 跨进程写同一 CSV 无保护

`write_lock` 仅是**进程内**锁；跨实例并发追加同一文件会交错写坏行/重复（与 P1 相关）。若要支持并行，见 P1 修复建议 b/c。

## 🟢 P6 .gitignore 与日期命名大文件不匹配

`.gitignore` 只忽略 `spec_id_pic_color_cnt.csv`，但实际大文件是日期命名（`spec_id_pic_color_cnt_260715.csv` 等，180 MB）。一旦 `git init`，这些文件会被整包提交。**建议补 `spec_id_pic_color_cnt_*.csv`、`spec_id_pic_color_cnt_*_*.csv` 或按需显式管理**（若仓库策略要入库小样本则例外）。

## 🟢 P8 环境/编码经验（非代码缺陷，备忘）

- spec_id.txt 是**无 BOM UTF-8**，CSV 是 utf-8-sig —— 一切外部处理须显式指定编码；
- 本机控制台/python stdout 默认 GBK → 中文输出乱码假象，python 命令加 `PYTHONIOENCODING=utf-8`；
- 反爬特征观察：连续解析失败比例升高是限流前兆（error_tasks 膨胀即信号）。
